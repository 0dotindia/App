scopes — `src/lib` + `src/app/actions`, `src/app/api`, `src/components` +

## Group A — Critical: security / account safety

### A1. 2FA enroll+confirm allow account takeover via a stolen API token
**Files:** `src/app/api/v1/account/two-factor/enroll/route.ts`,
`src/app/api/v1/account/two-factor/confirm/route.ts`
**Severity:** Critical

Neither route calls `requireCurrentPassword`, unlike every sibling
account-security mutation (password change, 2FA disable, recovery-code
regen). A bearer token scoped only `account:write` — no password knowledge
required — can enroll a new TOTP secret and confirm it, planting a durable
login bypass (valid 2FA + 10 recovery codes) that survives revocation of the
original token.

**Fix:** add `requireCurrentPassword(ctx.userId, body.currentPassword)` to
both routes before mutating state, mirroring `two-factor/disable/route.ts`
and `account/password/route.ts`. Add `enforceRateLimit` per user, matching
`confirm`'s sibling `disable`/`recovery-codes` routes. Update the mobile/web
2FA-enrollment UI to collect and send `currentPassword` if it doesn't
already.

### A2. Mobile sign-out can be silently undone by an in-flight token refresh
**File:** `mobile/src/api/client.ts:133` (`tryRefreshTokens`)
**Severity:** Critical

`tryRefreshTokens()` has no coordination with `AuthContext.signOut()`. A 401
can trigger a refresh; if the user signs out while it's in flight, the
refresh can still complete and rewrite valid tokens into SecureStore after
`clearTokens()` ran — silently re-authenticating the user on next launch.

**Fix:** add a module-level "signed out" epoch/generation counter (or an
`AbortController` cancelled by `signOut()`) that `tryRefreshTokens()` checks
before calling `saveTokens()`; if a sign-out happened during the refresh,
discard the result instead of persisting it.

### A3. Rate-limit IP extraction likely reads the wrong hop on Vercel
**File:** `src/lib/rate-limit.ts:165` (`getClientIp`)
**Severity:** Critical (needs verification against actual deployment)

`getClientIp()` takes the **last** comma-separated `X-Forwarded-For` value.
This was a deliberate fix (docs/BUGS.md item #6) for spoofability assuming
"exactly one trusted reverse proxy" — but Vercel's own convention is that the
client IP is the **first** value, with infra hops appended after it. If true
here, every distinct visitor can collapse onto one rate-limit bucket (mass
lockout) or a client can dodge the OAuth token endpoint's brute-force guard
by varying trailing hops.

**Fix:** verify Vercel's actual `x-forwarded-for` shape in this deployment
(check a real request in Vercel's request logs, or Vercel's platform docs for
the header contract), then switch `getClientIp()` to take the correct hop —
almost certainly the first non-empty value when running purely behind
Vercel's edge network with no additional upstream proxy. Add a code comment
recording which convention was verified and how, so this doesn't flip-flop
again.

## Group B — Critical: production availability

### B1. Custom-domain routing can fail platform-wide under ordinary load
**Files:** `src/proxy.ts`, `src/app/api/internal/custom-domain-route/route.ts`
**Severity:** Critical (live-site availability)

`proxy.ts`'s server-side `fetch()` to the internal lookup route never
forwards the original visitor's IP, so `getClientIp()` inside that route
always resolves to the literal string `"unknown"`. Every custom-domain
request platform-wide collapses onto one shared rate-limit bucket
(`custom-domain-route:ip:unknown`, 60/min). Once aggregate traffic across
*all* custom domains exceeds that, the lookup starts 429ing for everyone,
and `proxy.ts` falls through to normal 0dot.in routing — every custom domain
intermittently fails to resolve, unrelated to any actual abuse.

**Fix:** have `proxy.ts` forward the real client IP to the internal route
(e.g. an `x-forwarded-for` header set from the original request before the
internal `fetch()`), and have the internal route trust only that
server-to-server hop. Alternatively, rate-limit this internal route by a
different, more appropriate key (e.g. requested hostname) since it's an
internal lookup, not a public endpoint directly reachable by an attacker's
arbitrary IP anyway — pick whichever avoids the shared-bucket collapse while
still bounding worst-case DB load.

## Group C — High: DMCA legal/compliance (feature shipped in `b4e59d1`)

### C1. `/dmca` page publishes a placeholder as its live legal contact
**File:** `src/app/dmca/page.tsx:11` (`DESIGNATED_AGENT`)
**Severity:** High (legal/compliance, live + indexable)

Ship-blocking: real bracketed placeholder text
(`"[dmca@yourdomain — create this mailbox before shipping]"`) renders as the
actual designated-agent contact info on a public page, with nothing
preventing it from going live as-is.

**Fix:** source `DESIGNATED_AGENT` from environment variables
(`DMCA_AGENT_NAME`, `DMCA_AGENT_EMAIL`, `DMCA_AGENT_ADDRESS`) via
`requireEnv`-style helpers (matching `src/lib/email.ts`'s existing pattern),
so a missing value fails the build/boot instead of silently rendering a
placeholder. Get real values from the user before deploying; until then,
keep working against a `.env.example` entry and fail loudly if unset in
production.

### C2. Anonymous DMCA takedown filing has no rate limiting
**Files:** `src/app/actions/dmca.ts:13`, `src/lib/dmca.ts`
**Severity:** High

`fileDmcaTakedownNoticeAction` dropped its `requireVerifiedUser()` gate
(intentionally, to allow anonymous filers) but added no replacement
throttle, unlike every other anonymous-write action (`business-contact.ts`,
`newsletter.ts`), which both call `checkRateLimit`/`getClientIp`. Unbounded
anonymous submissions can flood a target with `notifyDmcaNoticeReceived`
notifications and create unbounded `TrustSafetyCase` rows, and — via the
strike-count auto-suspend path — could eventually be abused to bulk-suspend
accounts if any notices get rubber-stamped.

**Fix:** add `checkRateLimit`/`getClientIp`-based throttling to
`fileDmcaTakedownNoticeAction`, mirroring `business-contact.ts`'s shape
(per-IP, generous but bounded — e.g. 5/hour).

### C3. DMCA form is non-functional for "Comment" and mismatched for other types
**File:** `src/app/dmca/DmcaNoticeForm.tsx`
**Severity:** High (feature correctness)

- "Comment" content type has no URL-based resolution path in
  `resolveDmcaSubject` at all — any real complainant selecting it can never
  successfully file.
- The single shared "Link to the infringing content" field shows one static
  post-shaped placeholder regardless of the selected content type, even
  though articles (`/[username]/articles/[slug]`) and marketplace listings
  (`/m/[id]`) need different URL shapes — legitimate notices for those types
  get rejected with a generic "Couldn't find that content" error purely due
  to a UI/copy mismatch.

**Fix:** either (a) remove "Comment" from the content-type options until a
real resolution path exists (least effort, honest UX), or (b) implement
comment permalink resolution in `resolveDmcaSubject` if comments have (or
can be given) a stable public URL. Make the URL field's placeholder and
helper text change based on the selected content type, matching each type's
actual resolvable URL shape.

### C4. `resolveDmcaSubject` doesn't validate URL host
**File:** `src/lib/dmca.ts:62`
**Severity:** Medium

`new URL(trimmed, "https://0dot.in")` discards the parsed host and only uses
the path — a link to an unrelated external site with a coincidentally
matching path shape resolves against an internal 0dot.in resource.

**Fix:** parse the URL without a base, and explicitly reject (with a clear
error) any URL whose host isn't `0dot.in` (or is empty, meaning a bare
relative path was pasted — still fine to accept those).

### C5. Unhandled `decodeURIComponent` throw crashes the DMCA resolver
**File:** `src/lib/dmca.ts:85`
**Severity:** Medium

A malformed percent-encoded path segment (e.g. `50%zzoff`) throws an
uncaught `URIError`, crashing the action instead of returning "Couldn't find
that content."

**Fix:** wrap the `decodeURIComponent` call in try/catch, returning the
existing not-found error on failure.

## Group D — High: money correctness (wallet)

### D1. Wallet transfer idempotency key isn't bound to recipient/amount
**File:** `src/lib/wallet/transfer.ts:55` (`postTransaction`/`transferCoinsCore`)
**Severity:** High

Dedup is keyed purely on the client-supplied `idempotencyKey`, never on
`toUserId`/`coins`. Reusing a key with a different recipient or amount
silently no-ops (`created: false`) but the route still responds
`200 {ok:true}` — a caller checking only the status code believes a second,
different transfer succeeded when nothing moved.

**Fix:** include `toUserId` and `coins` in the idempotency check — either
store them alongside the key and compare on reuse (mismatch → explicit 409
"idempotency key already used with different parameters" instead of a silent
`ok:true`), or derive the stored key as a hash including those fields.

### D2. Wallet transfer velocity caps have a TOCTOU race
**File:** `src/lib/wallet/eligibility.ts:56` (`checkTransferVelocity`)
**Severity:** High

The 24h `CoinTransfer` read happens before the new transfer's insert, with
no row lock or DB constraint — two concurrent transfers from the same
sender can each read "under the cap" and both proceed, jointly exceeding
`TRANSFER_MAX_COINS_PER_DAY`/`TRANSFER_MAX_RECIPIENTS_PER_DAY`. The existing
code comment overstates what the surrounding transaction guarantees (only
ledger-balance atomicity, not velocity-check atomicity).

**Fix:** move the velocity check inside the same `db.$transaction` using a
`SELECT ... FOR UPDATE`-equivalent (Prisma: pessimistic lock via raw SQL, or
serializable isolation on the transaction) scoped to the sender, so
concurrent transfers from the same sender serialize on this check. At
minimum, re-check velocity *after* acquiring whatever lock `postTransaction`
already takes on the sender's ledger row, so the two checks share the same
critical section.

## Group E — Medium: post-interaction races

### E1. Like/unlike route TOCTOU
**File:** `src/app/api/v1/posts/[id]/like/route.ts:23`
**Severity:** Medium

Existing-like lookup runs outside the transaction; a double-tap races two
requests that both see "not liked," both attempt `create`, and the second
throws an unhandled 500 on the unique-constraint violation instead of the
idempotent un-like the route's own comment promises.

**Fix:** move the existence check inside the `db.$transaction`, using `tx`
for both the read and the write — same pattern already used for reposts
(`toggleRepost`, per docs/BUGS.md item #5) and recommended for bookmarks
below.

### E2. Bookmark route: same TOCTOU
**File:** `src/app/api/v1/posts/[id]/bookmark/route.ts:27`
**Severity:** Medium

**Fix:** same as E1 — wrap read+write in one transaction.

### E3. Like/repost routes return stale counts
**Files:** `src/app/api/v1/posts/[id]/like/route.ts:45`,
`src/app/api/v1/posts/[id]/repost/route.ts:50`
**Severity:** Low

Response count is computed from a pre-transaction snapshot ± 1, not
re-read after the transaction commits — can be wrong under concurrent
activity on the same post.

**Fix:** re-read the count from the DB (or return it from within the same
transaction, post-write) instead of computing it client-side from the
snapshot.

## Group G — Medium: SSE streaming reliability

### G1. `enqueue` after `cancel` race in SSE streams
**Files:** `src/app/api/b/[slug]/viewers/stream/route.ts:42`,
`src/app/api/v1/communities/[slug]/chat/stream/route.ts:83`
**Severity:** Medium

`start(controller)` is `async` and awaits (a Redis/DB read) before
`unsubscribe`/`heartbeat` refs are assigned. A disconnect during that await
makes `cancel()` a no-op (refs still undefined); when the pending read
resolves, `controller.enqueue()` runs against an already-cancelled
controller and throws an unhandled rejection instead of being suppressed.

**Fix:** set a local `closed` flag (or check `controller.desiredSize === null`)
before every `enqueue()` call in `start()`, and have `cancel()` set that flag
immediately (even before `unsubscribe`/`heartbeat` exist) so the pending
`start()` await can check it once its own read resolves and skip the
enqueue.

### G2. SSE routes missing `maxDuration` / graceful proactive close
**Files:** `src/app/api/c/[slug]/voice/[roomId]/stream/route.ts` (missing
`maxDuration` entirely), `src/app/api/v1/communities/[slug]/voice/[roomId]/stream/route.ts`
(has `maxDuration=300` but no recycle), `src/app/api/v1/messages/stream/route.ts`
(dropped `STREAM_RECYCLE_MS` that its cookie-based sibling has),
`src/app/api/b/[slug]/viewers/stream/route.ts` (same, no recycle)
**Severity:** Medium

Missing `maxDuration` falls back to a much shorter platform default,
disconnecting listeners almost immediately. Missing the proactive
"close cleanly before the ceiling" pattern (present in
`v1/communities/[slug]/chat/stream` and the cookie-based `messages/stream`)
means Vercel force-kills the function at the timeout instead of letting the
client's `EventSource` reconnect gracefully — shows up as timeout errors in
logs instead of clean closes.

**Fix:** add `export const maxDuration = 300` to the voice stream route
that's missing it; add the same `STREAM_RECYCLE_MS`-based proactive
`controller.close()` (just under the 300s ceiling) to the three routes that
lack it, copying the exact pattern from
`v1/communities/[slug]/chat/stream/route.ts`.

## Group H — Medium: webhook observability

### H1. Stripe/LiveKit webhook signature failures are silently swallowed
**Files:** `src/app/api/stripe/webhook/route.ts:111`,
`src/app/api/stripe/webhook-v2/route.ts:42`,
`src/app/api/webhooks/livekit/route.ts:35`

Missing/renamed metadata on a platform-subscription checkout session causes
a silent early return — every sibling branch in the same function logs
before returning. A paid, unfulfilled checkout leaves no trace.

**Fix:** add `logger.warn("platform subscription checkout missing required metadata", { sessionId, metadata })`
before the early return.

## Group J — Mobile app fixes

### J1. LiveKit viewer error state can never render
**File:** `mobile/src/screens/LivestreamViewerBody.tsx:181`
**Severity:** Medium

`onError` sets `tokenError` but never clears `liveKitToken`; since the

### J2. Trust & Safety notifications misroute
**File:** `mobile/src/links/resolvePath.ts:90`
**Severity:** Medium

`reservedFirstSegment` regex is missing `"trust-safety"`, so

**Fix:** add `trust-safety` to the reserved-first-segment regex/list.

### J3. Realtime streams over-reconnect on transient AppState blips
**Files:** `mobile/src/screens/VoiceRoomBody.tsx:73`,
`LivestreamViewerBody.tsx`, `CommunityChatBody.tsx`,
`MessagesStreamContext` (all four call `setActive(AppState.currentState === "active")`)
**Severity:** Medium

Treats transient `"inactive"` (share sheet, permission dialog, control

full resync on every dismissed dialog. `mobile/src/utils/useAppForeground.ts`

**Fix:** have all four call sites use `useAppForeground` (or the same

### J4. Mobile markdown renderer missing ordered-list / `---` support
**File:** `mobile/src/lib/wiki-markdown.tsx:128`
**Severity:** Medium (content fidelity)

Only `"- "` bullets are recognized; ordered lists (`"1. "`) and horizontal
rules (`"---"`) fall into the plain-text branch and render as garbled
literal text, unlike the web renderer. Affects `ArticleDetailBody`,
`BookDetailBody`, `WikiDetailBody`, `BookChapterBody`.

**Fix:** add ordered-list-item and horizontal-rule branches to the
line-classification logic, mirroring the web renderer's handling
(rendering an ordered list container and an `<hr>`-equivalent).

### J5. `tryRefreshTokens` catch doesn't guard `clearTokens()`
**File:** `mobile/src/api/client.ts:140`
**Severity:** Low

An unguarded `await clearTokens()` inside the catch can itself throw
(e.g. SecureStore/Keystore failure), propagating a raw exception instead of
the documented "always resolves to false."

**Fix:** wrap `clearTokens()` in its own try/catch inside this catch block,
swallowing (with a log) any secondary failure so the function still resolves
to `false`.

### J6. `ProfileScreenBody` has no stale-response guard
**File:** `mobile/src/screens/ProfileScreenBody.tsx:143`
**Severity:** Low

Rapid refocus can fire overlapping `load()` calls; an older response
arriving after a newer one silently overwrites fresher state.

**Fix:** add a request-id/generation guard (increment a ref on each `load()`
call, only apply results if the ref still matches when the promise
resolves), same pattern commonly used for race-safe fetch-on-focus.

### J7. Voice recorder reads stale duration on stop
**File:** `mobile/src/utils/useVoiceRecorder.ts:24`
**Severity:** Low

`state.durationMillis` is only refreshed on a 200ms poll; stopping right
after a poll tick can compare a stale, understated duration against the
minimum-duration floor, silently discarding a legitimately long-enough
recording.

**Fix:** after `await recorder.stop()` resolves, read the actual final
duration from the recorder/URI (e.g. via the resulting file's metadata or
the recorder's post-stop status) instead of the last polled value, before
applying the minimum-duration check.

### J8. Voice-note playback duration label stuck at "0:00"
**File:** `mobile/src/components/MessageAttachmentBubble.tsx:77`
**Severity:** Low

After playback finishes, `status.currentTime` stays near `status.duration`
so the `currentTime > 0` branch stays true, showing `"0:00"` indefinitely
instead of reverting to the clip length.

**Fix:** check `status.playing || (status.currentTime > 0 && status.currentTime < status.duration)`
so a finished clip (currentTime ≈ duration) falls back to showing the full
clip length instead of the elapsed-remaining calculation.

### J9. `PostMediaGrid` keys by URL instead of position
**File:** `mobile/src/components/PostMediaGrid.tsx:16-17`
**Severity:** Low

**Fix:** key by `item.position` (already unique and available) instead of
`item.url`.

## Group K — Low: CSS specificity bug

### K1. `.mutedText` + `text-xs` silently does nothing
**Files:** `src/app/dmca/DmcaNoticeForm.tsx:44,79`,
`src/app/download/page.tsx:213` (pre-existing instance)
**Severity:** Low (visual)

`.mutedText` is an unlayered rule hardcoding `font-size: var(--text-sm)`;
Tailwind's `.text-xs` lives inside `@layer utilities`. Cascade Layers rules
mean the unlayered declaration always wins regardless of source/class order,
so combining them silently fails to shrink the text.

**Fix:** either move `.mutedText` into a layer that sorts before Tailwind's
utilities (so `text-xs` can override it), or stop combining the two classes
and instead give `.mutedText` a `small` size-variant class
(`.mutedText--sm` or similar) for the cases that need 0.8rem instead of the
default 0.9rem. Grep for any other `mutedText \S*text-(xs|sm|base|lg)`
combinations while in there.

## Group L — Low: admin/internal hardening

### L1. Admin debug route reinvents auth instead of using the shared guard
**File:** `src/app/api/admin/debug/oauth-scopes/route.ts:14`
**Severity:** Low

Hand-rolls a `platformRole !== "super_admin"` check instead of calling
`requirePlatformRole` from `src/lib/auth-guards.ts`, missing that helper's
rank-based comparison (added specifically to avoid a fail-open bug on an
unrecognized role string).

**Fix:** extract a pure `hasPlatformRole(userId, minRole)` (or accept an
`onFail` callback) from `auth-guards.ts` that both the redirect-based and
JSON-based callers can share, and use it here.

### L2. Same route hardcodes a first-party app name list
**File:** `src/app/api/admin/debug/oauth-scopes/route.ts:19`
**Severity:** Low

**Fix:** import `FIRST_PARTY_APPS` from `src/lib/first-party-apps.ts` and
derive the name list from it instead of a re-typed literal array.

### L3. Internal custom-domain-route uses the weaker in-memory rate limiter
**File:** `src/app/api/internal/custom-domain-route/route.ts:23`
**Severity:** Low (defense-in-depth; B1's fix addresses the main
availability bug)

`rate-limit.ts`'s own doc comment says `checkRateLimit` "is NOT acceptable
for guarding a credential check... those callers use `enforceRateLimit()`
instead" — this route uses the weaker one for host-enumeration protection.

**Fix:** switch to `enforceRateLimit`, once B1's IP-forwarding fix makes the
rate-limit key meaningful for this route.

## Group M — Low: misc correctness polish

### M1. Tip amount uses floating-point cents math
**File:** `src/app/api/v1/wallet/purchases/route.ts:50`
**Fix:** use an integer-cents-safe rounding approach (e.g.
`Math.round(Number(body.amount.toFixed(2)) * 100)` or a decimal library
already used elsewhere in the wallet code) instead of raw
`Math.round(amount * 100) / 100`.

### M2. `limit=0` on wallet transactions treated as "no limit"
**File:** `src/app/api/v1/wallet/transactions/route.ts:21`
**Fix:** parse with `Number.isFinite` + explicit `??` fallback instead of
`||`, so an explicit `0` isn't coerced to the default.

### M3. Admin trust-safety queue doesn't show the DMCA reported URL
**File:** `src/app/admin/trust-safety/page.tsx:107`
**Fix:** add `infringingContentLocation` to the rendered fields for
`dmcaTakedownNotice` cases so staff can see what was reported without
querying the DB.
