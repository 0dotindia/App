# 0dot — Judgment-Call Backlog: Phased Implementation Plan

## Context

Over a long session, five rounds of parallel read-only audits covered the entire web app (auth/landing, feed, profile, messages, settings, discovery, notifications, wallet, communities, org/business, developer/OAuth, admin, and peripheral settings). Clearly-safe fixes (missing `role="alert"`, deprecated props, token drift, a handful of confirmed TOCTOU races) were already applied and verified (`tsc`/`eslint`/live routes all clean). What's left is everything that was deliberately **not** auto-applied because it needed a human decision, touched shared/public-facing shape, or was large enough to deserve its own pass.

This plan sequences that backlog. Two follow-up verification passes (one on shared infra: reset-hook pattern, timezone utilities, upload cleanup, audit-log schema; one earlier on repost wiring) confirmed the concrete facts this plan is built on — cited inline below.

**Goal of the phasing:** fix the few things that are genuinely broken-and-risky first (P0), then do the handful of shared-infrastructure fixes that each resolve a dozen+ findings at once (P1) — these are the best time-to-impact ratio in the whole backlog — then work through contained one-off fixes (P2), and only then take up the pure product-decision items (P3), each of which needs a quick answer before it's worth writing code.

Status: not started. Picking this back up should start at P0.

## P1 — Shared infrastructure (highest leverage: each fix resolves 4–20 findings at once)

### P1.1 — `useActionState` reset-on-success hook (resolves 18 files / 20 call sites)

**Confirmed root cause:** these forms do `await formAction(formData); formRef.current?.reset();` right after dispatch. `useActionState`'s dispatch return isn't tied to completion, so the reset fires immediately regardless of whether the server action actually succeeded — a validation error clears the user's input while showing the error message on an empty form.

**Working reference fix already shipped this session:** `src/app/s/[username]/EpisodeForm.tsx` (lines ~30-38) — a `wasPending` ref + `useEffect` that resets only on the falling edge of `pending` with no `state?.error` present:

```tsx
const wasPending = useRef(false);
useEffect(() => {
  if (wasPending.current && !pending && !state?.error) {
    formRef.current?.reset();
    // + any extra local state to clear
  }
  wasPending.current = pending;
}, [pending, state]);
```

**Plan:** extract this into a shared hook, `useResetOnSuccess(formRef, pending, state, onReset?)`, taking an optional callback for forms with extra local state to clear.

- New file: `src/hooks/useResetOnSuccess.ts`
- **15 files drop in with zero customization** (just `useResetOnSuccess(formRef, pending, state)`):
  `BusinessLinksForm.tsx`, `NewContactForm.tsx`, `JobAlertForm.tsx`, `AddLinkForm.tsx`, `AddSkillForm.tsx`, `SocialLinksForm.tsx`, `GitRepositoryForm.tsx`, `ConnectExternalAccountForm.tsx`, `CredentialForms.tsx` (3 call sites in one file), `ShortLinkForm.tsx`, `CalendarEntryForm.tsx`, `ProjectCommentForm.tsx`, `ArticleCommentForm.tsx`, `ReplyForm.tsx`, `QuoteRepostForm.tsx`
- **3 files need the optional callback** for extra local state (mirroring `EpisodeForm`'s `durationS`/`descriptionValue` clearing):
  - `src/app/feed/ComposeBox.tsx` — clear `files`, `uploading`, `uploadError`
  - `src/app/s/[username]/ComposeCrossPostForm.tsx` — clear `files`, `contentValue`
  - `src/app/feed/PollComposeForm.tsx` — clear `options`
- Already safe, do not touch: `ChangePasswordForm.tsx`, `CommunityChatView.tsx`, `EpisodeForm.tsx` (this becomes the hook's first consumer instead of its own copy).

Effort: ~30 min for the hook + ~5 min/file × 18 files. Mechanical once the hook exists.

### P1.2 — Shared viewer-local time rendering (consolidates 4 duplicate implementations + a wider sweep)

**Confirmed root cause:** four independent, unexported, near-identical `relativeTime()` functions exist (`PostCard.tsx`, `c/[slug]/manage/page.tsx`, `b/[slug]/manage/contact/page.tsx`, `notifications/page.tsx`), each falling back to `date.toLocaleDateString()` for anything ≥7 days old — which runs **server-side** in these Server Components, rendering in the server's timezone, not the viewer's. A broader set of plain `.toLocaleString()`/`.toLocaleDateString()` calls in other Server Components (sessions list, org audit log, wiki history, payment refunds, appointments, etc.) has the same underlying problem for absolute timestamps.

The correct pattern **already exists and works** in three places — `PollBlock.tsx`, `MessageBubble.tsx`, `ConversationListItem.tsx` all render time client-side via `useState`/`useEffect`. This is the pattern to generalize, not invent.

**Plan:**
1. New client component `src/components/RelativeTime.tsx` — takes an ISO string or timestamp, renders "2h ago" / "3d ago" / falls back to a real date, computed client-side (mirroring `MessageBubble`'s existing approach) so it's always viewer-local. Use `<time dateTime=... suppressHydrationWarning>` to avoid SSR/CSR text mismatch warnings, matching how the existing client-side instances handle it.
2. Replace the 4 duplicate `relativeTime()` functions with `<RelativeTime>`.
3. Sweep the remaining flagged Server-Component `.toLocaleString()` call sites (`sessions/page.tsx`, `org/[orgId]/audit-log/page.tsx`, `c/[slug]/wiki/[wikiSlug]/history/page.tsx`, `admin/payments/refunds/page.tsx`, `b/[slug]/appointments/page.tsx`, and any others turned up by `grep -rn "toLocaleString\|toLocaleDateString\|toLocaleTimeString" src/app` minus the client components already verified safe) to use the same component.

Effort: ~1–2 hours (component + ~15 call-site swaps, mechanical each).

### P1.3 — Upload replacement leaves the old file orphaned (storage leak)

**Confirmed root cause:** `del` from `@vercel/blob` is imported nowhere in the codebase — no code path ever deletes a blob. `UploadResult` only returns `{ url }`; the internal random blob path is discarded after upload. **However** — Vercel Blob's `del()` accepts a full URL, not just a pathname, so this does *not* require a schema change: at each "replace" call site, the *old* URL is already sitting in the DB row being overwritten. The fix is read-old-URL-before-overwrite, then `del(oldUrl)` after the new upload+DB write succeeds.

**Plan:**
1. Confirmed first target: `uploadResumePdf`/`removeResumePdf` in `src/app/actions/resume.ts` (resume PDF replace/remove) — read `profile.resumePdfUrl` before the update, call `del()` after the new write commits (or on remove).
2. Audit the other "replace" call sites the same way (avatar upload, business documents, business card avatar, published files) — same pattern each time, not a shared abstraction needed since each is a single `if (oldUrl) await del(oldUrl)` after a successful write.
3. Wrap in a try/catch that logs but doesn't fail the request if `del()` errors (a stray orphaned blob is far better than a failed save because cleanup hiccupped).

Effort: ~20 min/call site once the first one is done and reviewed. Start with resume (already scoped), confirm the pattern, then sweep the rest.

### P1.4 — Platform-wide admin audit log (new capability, not a patch)

**Confirmed gap:** no `PlatformAuditLog` or equivalent exists. `OrganizationAuditLog` and `ModAction` are both scoped (org/community) with a near-identical shape and are the right template. Currently, admin actions on `/admin/**` leave scattered, non-uniform traces (a `logger.warn` here, an overwritten `grantedBy` column there) with no single queryable log.

**Plan:**
1. New Prisma model `PlatformAuditLog`, mirroring `OrganizationAuditLog`'s shape minus the org scope:
   ```prisma
   model PlatformAuditLog {
     id         String   @id @default(uuid())
     actorId    String?
     actor      User?    @relation(fields: [actorId], references: [id], onDelete: SetNull)
     action     String
     targetType String?
     targetId   String?
     metadataJson String?
     createdAt  DateTime @default(now())

     @@index([createdAt])
     @@index([action, createdAt])
   }
   ```
2. New helper `logPlatformAudit(...)` in `src/lib/admin.ts` (or similar), mirroring `logOrgAudit`'s exact signature/shape for consistency.
3. Thread it through the write sites that currently skip logging: `platform-roles.ts` (grant/revoke), `admin-wallet.ts` (`issuePromoGrant`, `adminAdjust`, refunds), `admin-account-recovery.ts` (code issuance).
4. Simple admin-facing list page at `/admin/audit-log` (mirrors `org/[orgId]/audit-log/page.tsx`'s existing structure almost exactly — reuse its layout).

Effort: ~2–3 hours (migration + helper + threading through ~5 action files + one list page).

## P3 — Product decisions (answer first, then the fix is usually trivial)

These aren't engineering ambiguity — they're calls only the product owner can make. Recommended default is marked.

1. **Business-card privacy gating.** The app's own documented spec says `isPrivate` only ever gates posts/links/portfolio — bio is intentionally public regardless. A business card's `socialLinks`/`email` fields (opt-in, owner-enabled) currently bypass the same private-follower gate the main profile enforces for `socialLinks`. Should an enabled card **override** the account's privacy setting (current behavior — "this card is my deliberate public face"), or should it **respect** the same gate as the main profile? *No default recommendation — this is a real privacy-policy call.*

2. **Repost feature completion.** The CSS for a "pressed" repost state already exists but the data plumbing (which posts the viewer has reposted) was never finished — reposts never show as toggled and have no optimistic UI, unlike Like/Bookmark/Poll-vote. Confirmed scope: 15 files including 5 public `/api/v1/*` routes. Recommend: **do it** — it's a real, visible inconsistency for any user who reposts, but flagging the public-API surface change explicitly since that's usually worth a heads-up.

3. **Pending-follow ("Requested") state.** Only the main profile page shows "Requested" for a pending private-account follow; followers/following lists, the contextual rail, and the blocked-users page all just keep showing "Follow" forever after a pending request (silent no-op on repeat click). Recommend: **fix** — thread the pending-status set through `UserListItem` and its ~4 call sites, same shape as the `likedPostIds`-style sets already used elsewhere.

4. **`/trending` has no page header at all** (no title/eyebrow, unlike `/explore`'s full `PageHeader`). Needs a one-line copy decision (e.g. "Trending" + a short description) — mechanical once the copy is decided.

5. **Search has no pagination on any of its 8 result tabs** (hard `take: 20` cap, no "load more"). The file's own extensive spec comments suggest this may be a deliberate phase-6/7 scope cut for the SQLite-no-FTS setup. Confirm: intentional cut (leave as-is, maybe add a "showing top 20" note) vs. build out real pagination now (bigger — touches all 8 `search*()` functions plus a shared cursor pattern).

6. **Course pricing UI says "Price (coins)"** but the field is actually USD-denominated (converted to coins at settlement, correctly). Recommend: **fix the copy** to "Price (USD)" or similar — the conversion logic is already correct, this is purely a mislabeling.

7. **Push/email notification-settings labels read as full sentences** (e.g. "Push notifications for: Your ticket purchase is confirmed") because they reuse `getNotificationVerb`, shared with the live notification feed. Needs a short-label variant for settings rows specifically, or accept the current phrasing. Recommend: add a short-label map for settings display only, leave the feed's own copy untouched.

8. **Admin coin-grant idempotency semantics** (see P0 #1 for the bug itself) — once idempotency is wired up, what should "the same admin issues the identical grant again within N seconds" mean? Deduped (safe default, matches every other coin-spending path in the app) vs. always allowed (an admin might legitimately want to grant the same amount twice in a row). Recommend: **dedupe**, matching the rest of the codebase's convention — flag this as the default unless an explicit override affordance is wanted.

## Sequencing recommendation

1. **P0 first**, in listed order — each is small and independent, no reason to delay.
2. **P1.1 (reset hook) next** — biggest file count, fully mechanical once the hook exists, zero product ambiguity.
3. **P1.2 (RelativeTime) and P1.5 (100vh sweep)** — similarly mechanical, can run in parallel with P1.1.
4. **P1.3 (upload cleanup) and P1.4 (audit log)** — slightly bigger, do after the quicker P1 wins land.
5. **P2** — knock out opportunistically, no dependencies between them.
6. **P3** — resolve via a short round of questions before touching code; each answer unlocks a small, mechanical follow-up.
